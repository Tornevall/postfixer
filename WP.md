# The new Postfix Maildir all-in-one solution

Time flies. What worked years ago does not necessarily work now, especially when the original instructions already had a few missing pieces that later had to be documented separately.

My old [Postfix Maildir guide](https://www.tornevalls.se/the-postfix-maildir-guide/) dates back to 2019 and was built around an Ubuntu generation where this stack was much easier to assemble from distribution packages. Even then, the first article was not quite enough.

One of the follow-ups became [Postfix smtpauth and clients without imap/pop-auth](https://www.tornevalls.se/postfix-smtpauth-and-clients-without-imap-pop-auth/), because SMTP authentication needed more work than the first document covered.

So I am doing it again.

This time the goal is not another collection of commands that happens to work on one server. The new setup is being turned into an installer with explicit Ubuntu release handling and a repository that can also hold the actual Postfix configuration.

The project is called **Postfixer**.

## One repository instead of scattered server notes

The installer currently targets Ubuntu 18.04, 20.04, 22.04 and 24.04.

The older releases remain useful when rebuilding or recovering existing systems, while newer Ubuntu releases have their own problems. Courier is a good example. The packages and configuration layout that were available on older systems cannot simply be assumed to exist on a newer installation.

Postfixer therefore has one main installer:

```text
bin/install.sh
```

The release-specific details are separated into:

```text
bin/18.04.sh
bin/20.04.sh
bin/22.04.sh
bin/24.04.sh
```

Shared installation and repair logic stays in `bin/common.sh` instead of being copied into four almost identical scripts.

## A clean server does not have /etc/postfix yet

There is another fairly obvious problem with keeping the repository itself in `/etc/postfix`: a completely new server may not even have Postfix installed yet.

The repository now solves that by keeping the source configuration in its own directory:

```text
etc-postfix/
```

The installer first installs Postfix and lets the Ubuntu package create `/etc/postfix`. Configuration stored in `etc-postfix/` can then be applied on top of it.

That also makes it possible to keep the installer and the server configuration in the same repository without pretending that the Git checkout itself is a system directory.

My current production configuration can be added there later. Until then the installer works with the Postfix configuration generated by the package.

## What the installer prepares

The current stack includes Postfix, Cyrus SASL, saslauthd, Courier IMAP and POP3, PAM authentication, SpamAssassin, ClamAV, SPF policy handling, Postgrey, OpenDKIM, OpenDMARC, Fetchmail and Procmail.

The two authentication paths are deliberately separate:

```text
SMTP:
Postfix -> Cyrus SASL -> saslauthd -> PAM -> local Unix accounts

IMAP/POP3:
Courier -> authpam -> PAM -> local Unix accounts
```

This is also where some of the old "it worked on the previous server" assumptions needed to disappear. Courier configuration is not hardcoded to a single directory. The installer detects both the older `/etc/courier` layout and newer standalone Courier layouts such as `/usr/lib/courier-imap/etc`.

When Courier provides `.dist` templates and `sysconftool`, its own configuration upgrade mechanism is used rather than blindly replacing configuration files.

## Certificates are not issued by this server

This installation does not run Certbot to request or renew certificates.

My certificates are created elsewhere and synchronized to the mail server under:

```text
/etc/letsencrypt
```

Postfixer reads the certificate from there, verifies that the certificate and private key belong together, and creates the combined PEM files Courier needs.

The replacement is atomic and Courier is only restarted when the certificate content has actually changed.

After the external certificate job has synchronized a new certificate, deployment on the mail server is simply:

```bash
sudo make cert
```

## Hash maps should be built because Postfix needs them

One thing I wanted to get rid of was the traditional shell script containing a list of files that somebody once decided needed `postmap`.

Postfixer reads the active Postfix configuration instead.

Files actually referenced as `hash:` maps are rebuilt with `postmap`. Alias maps are handled with `postalias`. A file used as a `regexp:` map is not given a pointless `.db` file just because it happens to live in `/etc/postfix`.

Applying repository configuration therefore becomes:

```bash
sudo make apply
```

That copies `etc-postfix/` into `/etc/postfix`, rebuilds the maps that are actually configured, validates Postfix and reloads it.

## Installation

The repository is available at:

[github.com/Tornevall/postfixer](https://github.com/Tornevall/postfixer)

Installation starts with:

```bash
git clone https://github.com/Tornevall/postfixer.git
cd postfixer
sudo make install
```

The installer detects the Ubuntu release and selects the matching installation path.

Before an existing mail configuration is changed, a timestamped backup is stored under `/root/postfixer-backup-*`.

Some useful maintenance commands are:

```bash
sudo make apply
sudo make maps
sudo make cert
sudo make check
sudo make restart
```

The repository is also where the production Postfix configuration will live once I have cleaned it up enough to move it from the existing mail server into `etc-postfix/`.
